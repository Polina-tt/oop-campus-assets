# Лабораторна робота №1: Налаштування середовища розробки, структура C++-проєкту та компіляція за допомогою GCC і CMake

## 1. Мета роботи
Навчитися працювати з C++-проєктом у Visual Studio Code та середовищі Linux/WSL/Docker, опанувати етапи компіляції (препроцесинг, компіляцію, компонування), розділяти код на `.hpp` та `.cpp` файли, а також збирати проєкт за допомогою GCC та CMake.

## 2. Середовище та інструменти
* Маршрут: Windows + WSL
* Використані версії інструментів: `g++` (GCC), `CMake`, `GDB`

## 3. Структура проєкту
* `include/equipment_record.hpp` — оголошення структури даних обліку
* `src/equipment_record.cpp` — реалізація допоміжних функцій
* `src/main.cpp` — точка входу (головна програма)
* `CMakeLists.txt` — файл конфігурації CMake

## 4. Команди збірки та запуску

**Ручна компіляція через g++:**
```bash
g++ -Wall -Wextra -Iinclude src/equipment_record.cpp src/main.cpp -o app
./app

mkdir build && cd build
cmake ..
cmake --build .
./app
```



# Лабораторна робота №2: Класи, інкапсуляція та інваріанти. Робота з Git і статичний аналіз коду

## 1. Мета роботи
Перетворення структури даних `EquipmentRecord` на клас `EquipmentItem` із закритою внутрішньою логікою (інкапсуляція), забезпечення інваріантів класу, контроль допустимих переходів станів, налаштування процесів розробки через Git та автоматизація перевірок за допомогою статичних аналізаторів коду.

## 2. Призначення класу EquipmentItem
Клас `EquipmentItem` призначений для безпечного представлення та обліку університетського обладнання. Він повністю інкапсулює внутрішній стан та забезпечує суворий контроль над допустимими переходами об'єкта.

## 3. Перелік інваріантів класу
1. Ідентифікатор об'єкта (`id`) обов'язково повинен бути більшим за нуль.
2. Назва обладнання (`name`) не може бути порожнім рядком.
3. Категорія обладнання (`category`) не може бути порожнім рядком.
4. Нове обладнання при створенні автоматично переходить у початковий стан `Available` (Доступне).

## 4. Допустимі переходи стану
* `Available` -> `InUse` (Видача обладнання)
* `InUse` -> `Available` (Повернення обладнання)
* `Available` -> `UnderMaintenance` (Передача на технічне обслуговування)
* `UnderMaintenance` -> `Available` (Завершення обслуговування)

*(Будь-які інші переходи суворо відхиляються логікою класу та викликають виняток).*

## 5. Використані аналізатори та обґрунтування
* GCC warnings (`-Wall -Wextra -Werror`) — знаходить помилки на етапі компіляції та забороняє збірку проєкту за наявності попереджень.
* clang-format — перевіряє дотримання стилю кодування (відступи 4 пробіли, обмеження довжини рядка).
* Cppcheck — здійснює незалежний статичний аналіз вихідного коду на наявність логічних помилок.
* Clang-Tidy — глибокий лінтер (групи: `clang-analyzer-`, `bugprone-`, `performance-*`).

## 6. Опис обов’язкового експерименту
* **Коректна версія:** Скрипт `./scripts/check_quality.sh` запускається успішно і повертає код 0.
* **Навмисний дефект:** У код файлу `src/equipment_item.cpp` було тимчасово додано невикористану змінну `int unused_var = 42;`.
* **Результат:** Інструмент Clang-Tidy під час кроку `[5/6]` виявив проблему `warning: unused variable 'unused_var'` та перервав збірку проєкту з ненульовим кодом помилки через прапорець `WarningsAsErrors: '*'`.
* **Виправлення:** Невикористану змінну було видалено, після чого повторний запуск скрипту пройшов успішно.




# Лабораторна робота №3: Конструктори, час життя об’єктів і композиція класів

## 1. Мета роботи
Проєктування предметної області з декількох класів, розмежування відповідальностей, використання конструкторів зі списками ініціалізації, реалізація зв'язків композиції та асоціації між об'єктами, визначення власників об'єктів, побудова UML-діаграми та адаптація Bash-скрипту перевірки якості коду до зростання проєкту.

## 2. Розподіл відповідальностей та зв'язки класів
* `EquipmentItem` — представляє окрему одиницю обладнання та контролює її стан.
* `Location` / `Room` — описує фізичне приміщення/аудиторію, де зберігається обладнання *(Зв'язок: Асоціація)*.
* `EquipmentInventory` — керує колекцією обладнання, забезпечує пошук та облік *(Зв'язок: Композиція, володіє об'єктами `EquipmentItem`)*.

## 3. Інваріанти та правила володіння
* Усі конструктори використовують списки ініціалізації для гарантії коректного стану об'єкта одразу після створення.
* Об'єкти-власники керують часом життя вкладених компонентів (порядок конструювання: від вкладених об'єктів до обгортки; порядок знищення — зворотний).
* Невдалі операції не залишають систему в частково зміненому стані.
